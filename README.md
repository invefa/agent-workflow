# Agent工作流规范

本文汇总Agent在日常协作中的固定要求：交互方式、文档怎么写、目录文件怎么整理、图与文档怎么做出来、交付前怎么自查，以及实施中遇到的问题与可移植参数。可以直接作为系统提示或项目规范交给其他Agent。

除字符层面的硬规定外，其余各条都是取向而非铁律。判断标准始终是三条：同一份交付物内一致、看起来美观协调、AI味不重。具体情境与某条字面要求冲突时，按这三条判断，不要死守规则。

全文按性质分三块：第一节到第九节是通用要求，第十节是实施中遇到的问题与修正，第十一节是可直接照抄的参数。

## 一、交互方式

- 用户提问时先找答案，不要一收到问题就动手改文件。先给结论与依据，再说明可以怎么处理，由用户决定是否执行。
- 陈述平实。做成了写做成了，没做成写清卡在哪。不辩解，不自贬，不加"非常遗憾""所幸"这类修饰。
- 用户指出错误时，先确认错误的性质：是我理解偏了，还是规则本身写错了。前者改做法，后者改规则，两件事都要说清楚。规则写错时顺手把规则文件也改掉，否则下次还会照着错的做。

## 二、文档书写规范

### 2.1 字符与标点

- 任何位置都不要emoji，包括标题、列表、强调和对话里的临时说明。
- 不用Unicode特殊字符：箭头、破折号、弯引号、省略号字符一律避免，只用键盘能直接打出来的字符。表示因果与先后关系写`->`，对话里也一样。
- 中文正文用中文标点（逗号、句号、冒号、分号、括号），代码、路径、URL、英文列表内部保持半角，不混用。
- 专有名词首字母大写；缩写全部大写，除非该缩写有通行的小写写法。
- 英文与汉字之间不写空格。写`Agent工作规范`，不写`Agent 工作规范`。

### 2.2 措辞与句式

- 人称用"我"或省略主语，不用"我们"指代单个作者。
- 不用比喻和拟物化表达。判断标准是这个词放进内部系统说明、接口文档或工作邮件里会不会显得奇怪，会就不要用。把重要证据说成"最值钱"的证据，就属于这一类。
- 不用AI盛行之后才泛滥的抽象名词，例如缺口、抓手、闭环、赋能、痛点，判据同上。
- 不用AI味句式与套话。最扎眼的是否定再给定义，以及把数字堆进短句。常见替换如下。

| 不要写 | 换成 |
|---|---|
| 不是X，而是Y | 直接写Y是什么，不要先否定再定义 |
| 不是A，不是B，也不是C，而是D | 同上。级联否定再收束到定义，是最扎眼的一种 |
| 不仅仅是X，更是Y | 直接说X和Y各自是什么 |
| 值得注意的是 / 需要指出的是 | 直接写那件事，或用"这里""另外" |
| 让我们来看看 | 删掉，直接开始 |
| 深入剖析 / 一探究竟 / 揭秘 | 分析 / 查看 / 说明 |
| 在当今xx的背景下 | 删掉 |
| 这为我们提供了一个新的视角 | 删掉，或写出具体是什么视角 |

- 综上所述、总而言之、总之属于正常书面语，用得不密就不必回避，不要为了躲它们把句子改别扭。
- 不要在一串短句里塞一堆数字。密集数字连读很累，需要罗列数据时改用表格或分点。

### 2.3 标题与编号

- 标题精简，写成名词短语或动宾短语，不口语化，不在标题里加大段括号注解。
- 不滥用引号做强调。
- 用词专业且贴合上下文，不堆形象化但生僻的词。2.2对措辞的限制（比喻说法、AI泛滥的抽象名词）同样约束标题。

编号规则要按场合区分，不要一刀切：

| 场合 | 编号方式 |
|---|---|
| 正式文档的一级标题 | 用"一、二、三"加顿号，例如`一、全景` |
| 正式文档的二级标题 | 用数字，例如`2.1`、`2.2`，数字取父级在阿拉伯计数下的序号 |
| 索引类文档、README的行前缀 | 不要用"一、二、"这类编号，与"非题解文档不编号"一致 |
| 文件名与目录名 | 两位序号连号，`01`到`99` |

两条边界独立，都容易越界：

- "一级可以用汉字"不等于"各级都用汉字"。二级用数字是常见做法，不必跟着一级改成`（一）（二）`。
- "索引类文档不编号"只约束索引类文档的行前缀，不要扩大到所有文档的所有标题。

### 2.4 列表与表格

- 列表与候选项里，条目名称和它的解释之间必须留空行，不要紧贴，否则层次分不清。
- 对照类内容用表格：状态映射、措辞对照、工具可用性。
- 表格单元格里的竖线转义成`\|`，否则列会错位。
- 代码块标语言，命令和输出分开。
- 提到本地文件用可点击的相对路径，远端路径直接写绝对路径。
- 图片放在能说明问题的地方，并在正文里用一句话说清它说明了什么。

## 三、命名与文件组织

### 3.1 命名

- 目录名和文件名尽量短，只保留能区分彼此的信息，没有信息量的词一律去掉。
- 命名不设死规则。下划线、中线和大小写都可以用，也允许混用，具体情况具体分析。
- 按语义分组决定用哪种分隔：属于一个整体的部分，用下划线或首字母大写连起来；语义上不强相关的部分，用中线分开。`user_api_client.py`用下划线，说明这三段合起来才是这一个东西；`report-v2-final.pdf`用中线，说明这三段是并列的限定。
- 同一批文件内保持一致。一致性比任何单条规则都重要，看起来协调舒服即可，不要死守规则。
- 不用空格与中文。
- 同一批文件用两位序号连号。
- 一个主题一个文件，内容太长就按主题拆开。
- 索引与README自包含，相对链接不能指到交付单元外面。

### 3.2 目录结构

一个交付单元就是一个目录，内部按用途分层，同一层不混放不同类别的东西。图片的源文件、产物与生成脚本放在单元内的`fig`子目录，不混进正文：

```text
<deliverable>/
  <deliverable>.md   正文
  <deliverable>.docx 文档产物
  <deliverable>.pdf  PDF产物
  build-doc.py       文档生成脚本
  fig/
    01-xxx.drawio    图源文件
    01-xxx.png       位图产物
    01-xxx.svg       矢量产物
    make-figures.py  图的生成脚本
```

要点：

- 图与图的产物放`fig`，正文目录只留文档与文档生成脚本；正文引用写`fig/01-xxx.png`。
- 图的源文件、产物与生成脚本同放`fig`，脚本可重跑，产物可删除重建。
- 文档生成脚本放交付单元根目录。
- 序号用两位，`01`而不是`1`，排序稳定。
- 改名时正文里的引用必须同步改，否则链接失效。这一步最容易漏。

### 3.3 文件放置

- 不把临时脚本写到系统temp目录。
- 一次性工具与脚本放在当前工作区下自建的工作文件夹里，文件夹名简短清晰，内部按类别分好目录。
- 中间产物（探测文件、渲染预览、缓存）集中放在工作区下的一个工作目录里，交付前清掉，不要留在交付目录里。
- 改写既有文档前先确认它有没有版本历史，没有就先备份。

## 四、视觉呈现

### 4.1 配色

配色不设固定色板，不要把色值写死。真正的要求只有两条：

- **一致性**

  同一份交付物内，同一语义用同一个颜色。

- **可解读性**

  颜色承载语义，不是装饰。强调色只承担一个语义，不因为好看而加色。

在此之上：

- 简洁大方，不用花哨配色，也不用AI默认那类配色（高饱和蓝紫渐变、糖果色卡片那一类）。
- 常规元素用中性灰。
- 同图多系列优先用透明度或线型区分层次，不轻易换色。

下面是参考取向，不是硬性规定，任何场景都可以替换具体色值：

| 用途 | 参考取向 |
|---|---|
| 主文字与数值 | 接近纯黑的深灰 |
| 次要文字 | 中灰 |
| 常规描边与连线 | 浅灰 |
| 次级框与容器 | 更浅的灰 |
| 强调色 | 只选一种，只表达一个语义 |

### 4.2 形体与层级

- 不用半透明色块标签、大圆角灰底卡片、胶囊标签和重色填充。
- 层级手段按优先级排列：线宽、字号、字重，最后才是颜色。
- 默认不填充（`fillColor=none`），需要区分层次时才用极浅底色。
- 圆角保持小而可见（`rounded=1;arcSize=4`），不要大圆角，也不要完全去掉。

### 4.3 版式

- 版式紧凑，四边与纵向节奏均衡。
- 外边距、列间距、纵向间隔成体系，不要随手给值。
- 容器左右边界与首尾节点对齐，标题、副题、图形、容器共用一条左基准线。
- 做完检查两件事：右边距是否等于左边距，纵向各段间隔是否接近。

## 五、图形制作

### 5.1 工具链

用drawio桌面版的命令行生成，源头是mxGraphModel XML，产物是`.drawio`源文件加`.png`位图加`.svg`矢量。

```powershell
$exe = "<drawio可执行文件路径>"
& $exe -x -f png -e -s 3 -b 14 --theme light -o "$d\01-xxx.png" "$d\01-xxx.drawio"
& $exe -x -f svg -e -b 14 --theme light -o "$d\01-xxx.svg" "$d\01-xxx.drawio"
```

参数含义：

| 参数 | 作用 |
|---|---|
| `-x` | 导出模式 |
| `-f` | 输出格式 |
| `-e` | 把可编辑XML内嵌进产物，便于拖回编辑器继续改 |
| `-s` | 缩放倍率，用整数倍 |
| `-b` | 四周留白 |
| `--theme light` | 固定浅色主题 |

### 5.2 画布尺寸

画布宽度控制在600px上下。理由是文档渲染时图片会等比缩到容器宽，画布一旦超过容器宽，图里的字号会被一起缩小到看不清。宁可纵向多几行，也不要横向铺得很宽。

导出倍率用整数（建议3）。倍率不只影响清晰度，还影响字体的栅格化质量：非整数倍率（如1.5）会让标签先按低倍栅格化再缩放，字边发虚。实测同一区域在scale=1.5下发软，scale=2以上才实。

### 5.3 实现要点

- 标签文本走统一的规范化函数：去掉英文与汉字之间的空格，再做XML转义。
- 需要两行式节点（粗体标题加一行灰色摘要）时，HTML标签本身也必须写成实体（`&lt;b&gt;`），因为XML属性值里不允许出现裸的`<`。
- 生成后先校验再导出：用`xml.etree.ElementTree`解析一遍，不合法立刻报错。
- 导出子进程要设超时。drawio遇到非法输入不报错退出，而是挂住等交互。
- 导出后必须目检。导出成功不等于布局正确，元素重叠、文字溢出、连线穿过节点这类问题只有看图才发现。
- 加一道几何校验：解析XML，检查元素是否越出画布、估算文本宽度是否超出容器。

## 六、Word表格排版

### 6.1 要求

- 列宽必须按各列内容的实际长度动态分配，不能各列等宽。
- 表头一律居中，不受该列正文对齐方式影响。
- 正文对齐按内容性质判定，不按长度：句子左对齐，标签居中。只把中文句读当作散文信号，英文术语里的半角逗号不算。
- 以数字序号开头的列一律左对齐。居中会让01、02、09这类序号参差不齐，比左对齐更难读。
- 表头的区分手段从轻到重取舍：先用居中和下沿一条略重的线，不够再考虑别的。不要填充底色，不要加粗，也不要用黑体。黑体笔画本身比正文重，单换字体就等于强调，这几种手段叠起来表头会明显压过内容。
- 整张表宽度要填满正文宽度，不要右侧留空。
- 内边距要小、行高要紧凑，表格不能显臃肿。参考值：

| 项 | 参考值 |
|---|---|
| 左右内边距 | 2.5pt |
| 上下内边距 | 0.8pt |
| 单元格内段前段后 | 1pt |
| 正文行距 | 1.15 |
| 表头行距 | 1.05 |

### 6.2 折行要求

单元格折行后不允许末行只剩一两个字。末行要么占满一行，要么至少超过半行。宁可让整格多出一行，也要把折行撑匀。

### 6.3 列宽算法

要求看着简单，直接按内容比例分配却做不好。完整的做法分四步。

**第一步，量渲染后的文字，再估计字宽。** 宽度必须按实际渲染出来的文字量，不能按源码量。源码里的链接写成`[文件名](文件名)`，长度是渲染结果的两倍多，按源码量会把这一列的下限撑到两倍宽，相邻列被压得频繁折行。

估计字宽时不能用"非汉字一律半角"这种粗估：大写字母与`m`、`w`明显宽于半角均值，`ROMmon`这类混合大小写的缩写会被低估近三分之一，进而导致折行预测偏乐观。按字符分类估：

| 字符 | 占宽 |
|---|---|
| 汉字与全角符号 | 1.00 em |
| 大写字母 | 0.68 em |
| 小写字母 | 0.52 em |
| 数字 | 0.50 em |
| 空格 | 0.26 em |
| 其他半角符号 | 0.34 em |

**第二步，分清两个宽度口径。** 这是最容易出错的地方：

- 列宽 = 单元格实际宽度，含左右内边距。
- 文本区宽度 = 列宽减去两侧内边距。

分配列宽时用的是文本区宽度，设给单元格时用的是列宽。混用会让折行预测整体偏乐观一个内边距的量，表现为"预测一行放得下、实际差一点放不下"，末行甩出一两个字。

折行判断再加上0.94的安全系数。字宽是估算值，与实际排版总有偏差，宁可略早判定换行。

**第三步，定义代价函数。** 表格高度由同一行各列中行数最多的那格决定，所以不能按列独立求和：

```text
整表代价 = 各行最大行数之和 + 末行过短惩罚之和 * 权重
```

末行过短惩罚按绝对字数计，不按占列宽的比例。比例会失真：末行同样是3个字，在宽列里占比很小却和窄列一样难看。罚法是"末行不足3个字时，按缺的字数计"，权重取3.0。

权重需要实测标定。把权重从3提到12，末行过短的数量一个都不再降，说明瓶颈是固定总宽，继续加权重没有意义。

**第四步，坐标下降分配。** 先按内容量给初值，再用半个字宽为步长在列之间转移宽度：

```text
对每一对列 (a, b):
    试把半步从 a 移到 b,总宽不变
    整表代价下降则接受,否则还原
直到一轮下来没有任何转移被接受
```

保持总宽不变，表格自然填满正文宽度。

这里有一个退化情形必须单独处理。当每列内容都放得下时，整片区域的代价相同，下降算法找不到改进方向，会停在初值上，把富余宽度留在任意一列。表现为同一套算法在有的表上分配合理，在另一些表上却失衡。先判断是否所有列都放得下，若是则不存在折行取舍，直接把富余宽度按内容量比例摊开。

### 6.4 折行兜底

列宽确定后，逐格检查折行结果。若末行过短，自己算好均匀断行、显式插入换行符，不交给Word自动折行。Word自动折行只看宽度，不看观感。

留余量：显式断行的目标宽度是文本区的82%，断完之后还要检查每行不超过86%，否则估算偏差会让断好的行再次溢出，反而更难看。

这一步的效果明显，实测数据：

| 末行字数 | 处理前 | 处理后 |
|---|---|---|
| 不足3个字 | 43处 | 3处 |
| 不足2个字 | 12处 | 0处 |

### 6.5 其他表格属性

- 表头跨页重复（`w:tblHeader`）。
- 单行不被页面截断（`w:cantSplit`）。
- 表格用固定布局（`w:tblLayout type="fixed"`），同时设`tblGrid`与每个单元格的宽度。
- 表头行下沿加稍重的边线，与表体区分。
- 边线按边合并，不能每次调用都重建整组。只加一条下沿线时若把整组删掉重建，单元格其余的边会被一并抹去；表格外框失去显式设置后会回退到宿主程序内置样式的黑色边框，整张表因此变重。
- 边线元素要插在宿主元素规定的子元素位置上，不能一律追加到末尾，否则生成的文档可能被判定为损坏。

## 七、技术文档交付

### 7.1 文档结构

正式技术文档按下述结构组织：

| 部分 | 内容 |
|---|---|
| 封面 | 标题、副标题、细线、文档元信息 |
| 目录 | 章节标题加点线引导加页码，一级二级都列 |
| 正文 | 章节、段落、图、表 |
| 页眉页脚 | 页眉放文档名，页脚放页码；封面不显示 |

正文用宋体10.5pt首行缩进两字，标题用无衬线体加粗，层级靠字号区分（一级15pt，二级13pt）。

### 7.2 目录页码

Word的目录是域，由宿主程序在打开时重建。LibreOffice转PDF时不会重建目录域，加`w:updateFields`和给域标`w:dirty`都无效，PDF里只会留下占位文字。

可靠做法是自己算页码：

1. 把文档依次截断到第k个标题为止，转一次PDF。
2. 该PDF的总页数就是第k个标题所在页。
3. 截断只删除标题之后的内容，不影响之前的分页，所以结果与最终文档一致。
4. 把结果缓存成JSON，后续重建直接复用，不必每次重算。

取页数用渲染命令比读PDF内部结构稳，注意渲染命令在输出目录已存在时会直接失败，每次要换一个干净目录。

### 7.3 图片嵌入

python-docx不支持SVG，直接插入会抛`UnrecognizedImageError`。要在DOCX里保留矢量图，只能保存后手工改包结构：

1. 先按普通位图插入（这一步同时生成必需的PNG兜底部件）。
2. 解包，把SVG加入`word/media/`。
3. 在`word/_rels/document.xml.rels`里加一条image关系。
4. 在`document.xml`的`a:blip`节点内追加`a:extLst`，里面放`asvg:svgBlip`指向SVG。

这样Word 2016及以上取矢量，旧版本用PNG兜底。drawio导出的SVG每个标签都是`switch`包`foreignObject`加一张4倍超采样位图，即使渲染器不支持`foreignObject`，也会回退到位图而不是显示空白。

放图宽度按`画布宽度 / 100`英寸换算，使正文文字落在9pt左右，同时保证打印分辨率。

验证矢量的方法是把PDF按400DPI渲染再裁一块看，文字边缘锐利即证明是矢量；若是位图，这个倍率下必然糊。

## 九、代码书写规范

### 9.1 版式

代码版式按下面这套约定执行。项目里配了格式化工具的，把这些约定落进配置交给工具执行，不要手工维护排版。

- 缩进用4个空格，不用Tab。行宽上限100列，放不下先换行，不要为了减少行数牺牲可读性。
- 大括号跟在语句同一行（K&R）。函数、类、结构、命名空间、`if`、`for`、`while`都这样；只有跨多行的控制语句才把左大括号换到下一行。
- 单行的`if`、`else`、循环允许写成一行，不加花括号；类内短函数同理，例如`if (x) return;`。
- 连续的声明、赋值、宏定义、位域按列对齐，复合赋值也参与。中间出现空行或注释就断开，另起一组。
- 指针贴类型，写`int* p`；引用贴变量，写`int& r`。控制关键字与括号之间留一个空格，函数名与括号之间不留，括号内侧不加空格。
- 行尾注释与代码之间隔一个空格，连续几行的行尾注释对齐。
- `case`标签相对`switch`缩进一级；命名空间内容不缩进，C#用文件级`namespace`。
- 空行最多连续三行，块首允许保留空行。文本文件用LF；`.bat`用CRLF，否则cmd.exe解析会出错。
- 标识符按语言习惯：C系用小写下划线，必要时加模块前缀；C#类型与成员用PascalCase、局部变量用camelCase。同一项目内不混用。

C示例（示意）：

```c
typedef struct {
    int   length;
    int   capacity;
    char* data;
} sample_buffer;

static int sample_reserve(sample_buffer* buffer, int wanted) {
    if (wanted <= buffer->capacity) return 0;

    int   capacity = wanted * 2;
    char* data     = realloc(buffer->data, (size_t)capacity);
    if (data == NULL) return -1;

    buffer->data     = data;
    buffer->capacity = capacity;
    return 0;
}
```

C#示例（示意）：

```csharp
internal sealed class Sample {
    private string? _name;
    private bool _enabled;
    private bool IsOwned { get; private set; }

    internal bool TryApply(string name) {
        _name    = name;
        _enabled = false;
        IsOwned  = false;
        return true;
    }
}
```

## 十、问题与修正

每条的写法是：现象、当时以为的原因、真正的原因。

### 10.1 drawio导出无限卡死

**现象**：导出命令不返回，进程一直挂着，几十分钟后只产出一张尺寸明显不对的残图。

**当时以为的原因**：drawio渲染慢，或者文件太大。

**真正的原因**：单元格的`value`属性里写了裸的`<`（例如直接把`<b>`标签写进值里）。XML属性值不允许出现裸`<`，整个文件成为非法XML。drawio命令行遇到非法输入不报错退出，而是挂住等交互。

**正确做法**：HTML标签本身也写成实体；导出前先用`xml.etree.ElementTree`解析一遍做校验；给子进程设超时；判定导出成功不能只看"文件存在且非空"，残图也是非空的。

### 10.2 表格列宽退化成均分

**现象**：按内容分配列宽的算法跑出来是均分，一张表四列全是同一个宽度。

**当时以为的原因**：初值给得不好，或者权重没调对。

**真正的原因**：代价函数按列独立求行数之和。但表格高度由同一行各列中行数最多的那格决定，列内求和与真实高度无关，优化器找不到方向，退化成初值。

**正确做法**：代价函数按行取各列行数的最大值再累加。

### 10.3 折行预测偏乐观

**现象**：算法判断某格一行放得下，实际渲染却折了行，末行只剩一两个字。

**当时以为的原因**：字宽估算不准。

**真正的原因**有两个，叠加在一起。一是把"文本区宽度"当成"列宽"设给了单元格，两者差一个内边距（两侧各2.5到4pt）。二是"非汉字一律半角"的粗估，低估了大小写混合的英文缩写。

**正确做法**：分清两个口径，折行判断用文本区宽度；字宽按大小写与字符类别分别估；再加0.94的安全系数。

### 10.4 LibreOffice不重建目录域

**现象**：DOCX里有目录域，转出来的PDF目录是空的，只显示占位文字。

**当时以为的原因**：字段没标记为待更新。

**真正的原因**：目录在LibreOffice里属于"索引"而不是普通"域"，`w:updateFields`和`w:dirty`都管不到它，转PDF时不会重建。

**正确做法**：自己算页码，用截断法加缓存。

### 10.5 渲染命令在输出目录已存在时失败

**现象**：循环调用渲染命令，第一次成功，之后每次返回失败。

**当时以为的原因**：输入文件有问题。

**真正的原因**：渲染命令会尝试创建输出目录，目录已存在即报`EEXIST`直接失败。

**正确做法**：每次换一个干净的目录，或先删除再调用。同时让失败时抛出而不是静默返回空值，否则会连续失败却看不出原因。

### 10.6 改名后正文引用没同步

**现象**：重新生成后文档里若干张图不显示。

**当时以为的原因**：图表生成失败。

**真正的原因**：图片文件改成了新序号，正文里的图片引用还是旧文件名。这个错误是被另一处不一致（注入SVG的数量与图的张数对不上）顺带暴露出来的，否则不会发现。

**正确做法**：改名后跑一次链接有效性校验；排版脚本里对"引用到的资源数量"做一次断言，数量不符就报错。

### 10.7 列宽只在部分表上失衡

**现象**：同一套列宽算法，多数表分配合理，少数表却明显失衡。例如一列内容只有文件名却占了大半宽度，相邻的长句列被压得频繁折行。

**当时以为的原因**：初值给得不好，或者权重需要按表调整。

**真正的原因**：代价函数只在"有列需要折行"时才有梯度。出问题的那张表恰好每列都放得下自己的内容，整片区域代价相同，下降算法找不到任何改进方向，就停在了按内容量算出的初值上，把富余宽度留在了碰巧最宽的那一列。

**正确做法**：先判断是否所有列都放得下。若是，不存在折行取舍，直接把富余宽度按内容量比例摊开，不进入下降流程。

### 10.8 列宽按源码量计算

**现象**：某一列明显偏宽，相邻列被压得频繁折行。

**当时以为的原因**：那一列的内容确实长。

**真正的原因**：宽度按Markdown源码量。链接写成`[01-xxx.png](01-xxx.png)`，源码长度是渲染结果的两倍多，按源码量就把这一列的下限撑到了两倍宽，占掉全文宽度的七成。

**正确做法**：列宽、折行、对齐判定一律基于去掉标记后的可见文字。

### 10.9 边线重建把表格外框变黑

**现象**：表格整体看起来比设定重，外框明显深于内部线。实测外框RGB为(63,63,63)，内部线为(233,233,233)。

**当时以为的原因**：线宽或颜色设大了。

**真正的原因**：边线函数每次调用都先删掉整组边线再重建。给表头加下沿线那次只传了底边，于是表头单元格的上、左、右边线被一起抹掉；表格外框失去显式设置后，回退到了宿主程序内置表格样式的黑色边框。

**正确做法**：边线按边合并，保留未被提及的边。另外边线元素要插在宿主元素规定的子元素位置上，一律追加到末尾会让生成的文档被判定为损坏。

### 10.10 变量遮蔽把表格正文拆成单字

**现象**：渲染出来每张表的正文都是"一个字一个格子"，表头行却完全正常。

**当时以为的原因**：文档结构损坏，或者渲染器出错。

**真正的原因**：判定对齐的循环里，内层变量用了和函数外层"表格行集合"同名的名字，把它覆盖了。后面按行遍历时迭代的其实是字符串，按下标取出的是单个字符，于是每个字符各成一个单元格。

**正确做法**：内层变量不要复用外层集合名。更要紧的是补上内容层面的校验：段落数、表格数、列数、行数这些结构指标全部通过，也发现不了这个错误，只有抽查单元格内容的长度分布、把文档渲染出来看，才会暴露。
