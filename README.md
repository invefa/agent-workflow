# Agent工作流规范

本入口适用于所有任务。专题按任务读取，工具经验按遇到的问题查阅；不要求无条件加载整个仓库。

## 使用方式

用户说“遵守我的个人偏好”时，读取[个人偏好](preferences.md)，先确认适用范围，再按任务读取相关章节。个人偏好独立维护，不默认施加给其他使用者；本入口与专题继续提供通用规范。

| 当前任务 | 追加阅读 |
|---|---|
| 程序设计、代码修复、配置或数据行为变更 | [工程标准](engineering.md) |
| 文档、说明、命名或视觉表达 | [书写与组织](writing.md) |
| 准备验证、提交或交付 | [验证与交付](delivery.md) |
| 图形制作或Word排版 | 在相关专题基础上查[绘图参考](references/diagrams.md)或[Word参考](references/word.md) |
| 遇到相关工具故障 | 查[故障经验](references/troubleshooting.md)对应条目 |

代码任务同步改说明时，只追加相关书写章节。同一任务已读且未变化的规则不必重复加载；任务范围或规范版本变化时补读。专题细节不能削弱本入口的约束。

## 约束与适用范围

约束保护授权、数据和交付真实性，必须遵守。默认做法适用于没有更具体约定的情况，可根据任务调整。参考资料记录特定工具与环境下的经验，使用前核对条件。

用户本轮明确要求优先于仓库默认偏好；仓库专项规则在其范围内优先于通用默认。受到平台或工具强制限制时说明限制，不绕过。规则冲突影响授权或数据正确性且无法判断时再询问；纯格式取舍优先保持项目一致，不额外请求确认。

- 在授权范围内推进。咨询与讨论先给分析；执行请求直接完成必要工作，已有授权不反复确认。不可逆操作或实质扩大范围时确认缺失的授权。
- 保护用户和协作者的修改，不覆盖、回滚或提交不属于本任务的内容。写入前检查现状，破坏性操作前核对实际目标。
- 不泄露凭据、无关隐私和项目限定的内部信息。必要署名、公开身份及业务记录按交付对象处理。
- 如实区分观察、推测和已验证结论。没有运行的检查不写通过；失败或部分成功时写清当前状态和下一步。
- 测试专用的假数据、自动输入和绕过校验不得进入正常业务执行。实现与验证细则见[测试隔离](engineering.md#六测试与正式运行隔离)。

## 协作与上下文

先检查现有实现、适用规则和当前状态，再作决定。读取与问题相关的材料；定位后缩小搜索范围，避免反复输出整份日志、数据表或参考文档。

说明结论、依据和下一步，少写过程流水账。用户纠正时判断是理解、实现还是规范的问题，在本轮范围内修正相应来源，不只追加临时解释。

以我或省略主语表达，不用我们代指单个作者。回复、说明和交付材料遵守[技术书面语](writing.md#11-技术书面语)，具体语言与版式见[书写与组织](writing.md)。

## 规范维护

同一条规则只保留一个维护位置，入口和项目文件用链接引用。项目的目录、命令、技术选型和发布策略留在项目规范，不复制到通用标准。

新增规则须能帮助后续任务作出具体决定，并说明适用条件。先检查现有规则能否覆盖；一次故障先作为经验记录，条件稳定且可推广时再提炼成约束或默认做法。删除重复说明，失效经验标明或更新，避免不断叠加例外。

本仓库使用普通Markdown维护，不要求规则生成器、统一配置语言或额外工具框架。
