# Agent工作流规范

agent-workflow（简称 AWF）为项目提供通用工作规范和可按需查阅的工具经验。当前项目指 Agent 正在处理的项目。维护者的个人偏好可以单独启用。

## 使用方式

### 按项目启用

把下面这段加入当前项目的`AGENTS.md`或 Agent 实际读取的项目指令文件。入口也可以指向 Agent 可访问的本地检出。在线阅读时，从同一 GitHub 版本查找入口引用的相对路径。

```markdown
## 启用 agent-workflow

本项目启用 agent-workflow。开始任务时读取 [工作流入口](https://github.com/invefa/agent-workflow/blob/main/README.md)，按任务读取专题和工具经验。本项目的长期要求见本文件及其链接。

本项目已有的专项规则在其范围内优先于通用默认做法。规范入口无法读取时，说明情况，按当前任务和可用的项目规则继续。
```

### 固定版本

上面的入口会跟随 `main`。需要固定已验证的版本时，从 GitHub 的目标提交打开 `README.md`，将项目指令中的入口换成该页面的永久链接。固定入口的形式为 `https://github.com/invefa/agent-workflow/blob/<完整提交SHA>/README.md`。专题和参考资料也从同一提交读取。需要升级时，选定新提交，核对规则变化后更新入口。

### 按环境或任务启用

用户可以通过项目指令、用户级指令或单次任务启用通用规范。要采用本仓库的[个人偏好](preferences.md)，请明确要求“启用invefa的个人偏好”或直接指定该文件。项目或用户级指令也可以指定此来源并持续启用。

遇到“遵守我的个人偏好”一类简称时，从当前用户已配置或明确指定的来源读取。来源未确定且会影响本次工作时，先请用户指出偏好文件或链接。

## 约束与适用范围

约束保护授权、数据和交付真实性，必须遵守。默认做法适用于没有更具体约定的情况，可根据任务调整。参考资料记录特定工具与环境下的经验，使用前核对条件。

用户本轮明确要求优先于仓库默认偏好；仓库专项规则在其范围内优先于通用默认。受到平台或工具强制限制时说明限制，不绕过。规则冲突影响授权或数据正确性且无法判断时再询问；纯格式取舍优先保持项目一致，不额外请求确认。

- 在授权范围内推进。咨询与讨论先给分析；执行请求直接完成必要工作，已有授权不反复确认。不可逆操作或实质扩大范围时确认缺失的授权。
- 保护用户和协作者的修改，不覆盖、回滚或提交不属于本任务的内容。写入前检查现状，破坏性操作前核对实际目标。
- 不泄露凭据、无关隐私和项目限定的内部信息。必要署名、公开身份及业务记录按交付对象处理。
- 如实区分观察、推测和已验证结论。没有运行的检查不写通过；失败或部分成功时写清当前状态和下一步。
- 测试专用的假数据、自动输入和绕过校验不得进入正常业务执行。实现与验证细则见[测试隔离](standards/engineering.md#六测试与正式运行隔离)。

## 保持项目一致性

动手前先理解用户希望达成的结果、提出要求的原因，以及必须满足的约束。分清哪些做法是用户明确指定的，哪些是供参考的方案，哪些是 Agent 根据上下文推断的。结合现状排查问题，再确定改动范围。例如，用户说“保存没反应”时，先确认数据有没有写入、界面有没有反馈，再判断应修复写入、反馈还是两者。

根据现有证据推进。只有当不同理解会明显改变交付结果或授权范围，且现有材料不足以作出判断时，才向用户确认。交付前，用用户描述的场景验证结果。

先看项目的明确约定及有代表性的实例，再决定如何命名目录和文件、组织文档、表达同一概念、划分程序职责和编写代码。既有项目默认沿用其稳定做法。agent-workflow 的默认做法补充项目尚无约定的部分，可根据实际可读性和维护成本调整。遇到互相矛盾的先例时，以项目规范和最接近当前任务的有效做法为依据。

用户要求改变已有做法时，检查同一概念、同类入口、关联文档和引用是否受影响。维持此次变更正确性所必需的同步修改随任务完成。发现可以提升整体一致性、但会扩大范围的调整时，说明涉及哪些位置、为什么值得一起改，再询问用户是否纳入。已明确授权全局调整时，按授权范围推进。

## 协作与上下文

先检查现有实现、适用规则和当前状态，再作决定。读取与问题相关的材料；定位后缩小搜索范围，避免反复输出整份日志、数据表或参考文档。

质量优先于交付速度。在授权范围内把用户要求落实到可用的结果，为查证、修正和验证留出必要时间。交付前必须实际测试或检查，确认结果满足用户要求。发现缺项或问题时，修正后复测。具体做法见[验证与交付](standards/delivery.md#一按影响选择验证)。

拿不准事实、工具行为或实现细节时，主动查项目记录、阅读相关源码，或上网核对官方文档等可靠资料。需要确认实际行为时，做小范围验证。证据仍不足且会影响结果时，带着查到的信息向用户确认，并继续处理不依赖该决定的工作。

说明结论、依据和下一步，少写过程流水账。用户纠正时判断是理解、实现还是规范的问题，在本轮范围内修正相应来源，不只追加临时解释。

回复、说明和交付材料的表达、语言与版式见[书写与组织](standards/writing.md)。

## 规范维护

同一条规则只保留一个维护位置，入口和项目文件用链接引用。项目的目录、命令、技术选型和发布策略留在项目规范，不复制到通用标准。

通用规范按主题放在 `standards/`，个人偏好单独放在 `preferences.md`。工具与故障经验放在 `references/`，具名项目的案例和实现细节放在[项目案例](references/projects/)。可复制到其他项目的材料及配套脚本放在 [`templates/`](templates/)。从其他项目整理可复用经验时，按[经验记录与回馈](standards/project.md#三经验记录与回馈)处理。

新增规则须能帮助后续任务作出具体决定，并说明适用条件。先检查现有规则能否覆盖；一次故障先作为经验记录，条件稳定且可推广时再提炼成约束或默认做法。删除重复说明，失效经验标明或更新，避免不断叠加例外。

本仓库使用普通Markdown维护，不要求规则生成器、统一配置语言或额外工具框架。
