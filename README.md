# Agent工作流规范

agent-workflow 为项目提供通用工作规范与可按需查阅的工具经验。当前项目指 Agent 正在处理的项目。维护者的个人偏好可以单独启用。

## 使用方式

### 按项目启用

把下面这段加入当前项目的`AGENTS.md`或 Agent 实际读取的项目指令文件。入口也可以指向 Agent 可访问的本地检出。在线阅读时，从同一 GitHub 版本查找入口引用的相对路径。

```markdown
## 启用 agent-workflow

本项目启用 agent-workflow。开始任务时读取 [工作流入口](https://github.com/invefa/agent-workflow/blob/main/README.md)，按任务读取专题和工具经验。本项目的长期要求见本文件及其链接。

本项目已有的专项规则在其范围内优先于通用默认做法。规范入口无法读取时，说明情况，按当前任务和可用的项目规则继续。
```

### 按环境或任务启用

用户可以通过项目指令、用户级指令或单次任务启用通用规范。只有用户明确要求采用invefa的个人偏好时，才读取[个人偏好](docs/preferences.md)中适用的章节。用户可以在单次任务中说“遵守我的个人偏好”，也可以把启用要求写进项目或用户级指令。

### 按任务阅读

| 当前任务 | 追加阅读 |
|---|---|
| 程序设计、代码修复、配置或数据行为变更 | [工程标准](docs/agents/engineering.md) |
| 文档、说明、命名或视觉表达 | [书写与组织](docs/agents/writing.md) |
| 建立长期项目、维护项目指令、记录或总结经验 | [项目维护](docs/agents/project.md) |
| 准备验证、提交或交付 | [验证与交付](docs/agents/delivery.md) |
| 图形制作或Word排版 | 在相关专题基础上查[绘图参考](references/diagrams.md)或[Word参考](references/word.md) |
| 遇到相关工具故障 | 查[故障经验](references/troubleshooting.md)对应条目 |

代码任务同步改说明时，只追加相关书写章节。同一任务已读且未变化的规则不必重复加载；任务范围或规范版本变化时补读。专题细节不能削弱本入口的约束。

## 约束与适用范围

约束保护授权、数据和交付真实性，必须遵守。默认做法适用于没有更具体约定的情况，可根据任务调整。参考资料记录特定工具与环境下的经验，使用前核对条件。

用户本轮明确要求优先于仓库默认偏好；仓库专项规则在其范围内优先于通用默认。受到平台或工具强制限制时说明限制，不绕过。规则冲突影响授权或数据正确性且无法判断时再询问；纯格式取舍优先保持项目一致，不额外请求确认。

- 在授权范围内推进。咨询与讨论先给分析；执行请求直接完成必要工作，已有授权不反复确认。不可逆操作或实质扩大范围时确认缺失的授权。
- 保护用户和协作者的修改，不覆盖、回滚或提交不属于本任务的内容。写入前检查现状，破坏性操作前核对实际目标。
- 不泄露凭据、无关隐私和项目限定的内部信息。必要署名、公开身份及业务记录按交付对象处理。
- 如实区分观察、推测和已验证结论。没有运行的检查不写通过；失败或部分成功时写清当前状态和下一步。
- 测试专用的假数据、自动输入和绕过校验不得进入正常业务执行。实现与验证细则见[测试隔离](docs/agents/engineering.md#六测试与正式运行隔离)。

## 保持项目一致性

先看项目的明确约定及有代表性的实例，再决定如何命名目录和文件、组织文档、表达同一概念、划分程序职责和编写代码。既有项目默认沿用其稳定做法。agent-workflow 的默认做法补充项目尚无约定的部分，可根据实际可读性和维护成本调整。遇到互相矛盾的先例时，以项目规范和最接近当前任务的有效做法为依据。

用户要求改变已有做法时，检查同一概念、同类入口、关联文档和引用是否受影响。维持此次变更正确性所必需的同步修改随任务完成。发现可以提升整体一致性、但会扩大范围的调整时，说明涉及哪些位置、为什么值得一起改，再询问用户是否纳入。已明确授权全局调整时，按授权范围推进。

## 协作与上下文

先检查现有实现、适用规则和当前状态，再作决定。读取与问题相关的材料；定位后缩小搜索范围，避免反复输出整份日志、数据表或参考文档。

说明结论、依据和下一步，少写过程流水账。用户纠正时判断是理解、实现还是规范的问题，在本轮范围内修正相应来源，不只追加临时解释。

回复、说明和交付材料的表达、语言与版式见[书写与组织](docs/agents/writing.md)。

## 规范维护

同一条规则只保留一个维护位置，入口和项目文件用链接引用。项目的目录、命令、技术选型和发布策略留在项目规范，不复制到通用标准。

通用专题放在`docs/agents`，个人偏好单独放在`docs/preferences.md`，依赖工具、版本或特定场景的经验放在`references`。从其他项目整理可复用经验时，按[经验记录与回馈](docs/agents/project.md#三经验记录与回馈)处理。

新增规则须能帮助后续任务作出具体决定，并说明适用条件。先检查现有规则能否覆盖；一次故障先作为经验记录，条件稳定且可推广时再提炼成约束或默认做法。删除重复说明，失效经验标明或更新，避免不断叠加例外。

本仓库使用普通Markdown维护，不要求规则生成器、统一配置语言或额外工具框架。
