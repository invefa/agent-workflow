# 项目维护

适用于建立或接手长期项目、维护 Agent 项目指令和整理经验。项目指 Agent 正在处理的项目。先读[工作流入口](../README.md)，再结合当前项目的约定判断。

## 一、版本记录

明确项目需要长期维护时，先确认项目根目录及现有版本控制。如果项目还没有版本控制，且根目录不在现有 Git 工作树内，直接在项目根目录执行 `git init`，为后续变更保留版本和回退能力。已有仓库、工作树、子模块或其他版本控制时，沿用项目的安排。项目边界不清楚时，先核对归属。

在授权范围内建立可回退的提交基线。暂存前检查忽略规则与文件范围。初始化、首次提交和远端发布各有自己的结果，按[提交与协作](delivery.md#三提交与协作)处理。

## 二、维护项目指令

收到项目要求时，判断后续 Agent 是否会反复用到它。长期有效的行为约束、设计决定、命名与语言约定、常用验证入口和启用的工作流，适合写入项目的 `AGENTS.md` 或它引用的文档。一次性交付的内容、临时取舍和任务状态留在所属任务记录。对适用范围或长期有效性拿不定时，先问用户。

`AGENTS.md` 提供进入项目时需要的总览，写明项目的常用规则、适用范围和按需阅读入口。项目没有既定目录时，建议把供 Agent 查阅的专题规则、项目经验和交接记录放在根目录的 `.agents/` 下，按用途分类，并从 `AGENTS.md` 链接到相应文档。项目已有可用的组织方式时，可以沿用。规则已有权威来源时，总览保留定位所需的摘要和链接，具体条款在原处维护。

用户要求项目双语时，建议把 `AGENTS.md` 也纳入双语范围。保留 Agent 实际读取的入口文件，并按[双语文档约定](writing.md#12-语言与字符)维护两版的内容和语言切换链接。

## 三、经验记录与回馈

发现可重复应用的项目经验时，在本轮授权包含项目文档维护，或项目已授权持续记录经验的情况下，主动写到合适的项目文档，并在 `AGENTS.md` 里给出定位链接。只读任务将经验随回复提供。按用途归类，例如构建与验证、发布、故障处理。记录现象、成立条件、有效做法和验证结果，让接手者能判断何时适用。

用户要求“总结可复用经验”时，从当前项目的记录、改动和验证结果中提取经验，在总结里说明哪些适合留在当前项目、哪些能提炼成通用做法、哪些有参考价值但依赖特定工具、版本或环境。给出成立条件、证据和建议归属。总结请求本身的交付物是总结。写入当前项目按项目文档维护授权处理，写回 agent-workflow 按对该仓库的修改授权处理。

获授权写回 agent-workflow 后，把通用做法并入相应专题，依赖具体条件的案例放在[参考资料](../README.md#规范维护)。项目名称和具体实现细节留在案例中。合并已有同类条目，按来源项目的公开范围处理信息。提交和发布遵循[提交与协作](delivery.md#三提交与协作)。

## 四、重复操作与工具

同类操作反复出现时，判断它是否也会在其他任务或项目中重复，以及手工执行花费多少时间、容易在哪些步骤出错。先查项目已有的命令和脚本，再找适合的现成工具。选用前用代表性输入验证结果，确认工具能覆盖所需场景。

找不到合适工具，且重复频率、出错成本或跨项目需求足以支持投入时，向用户说明重复操作、已查过的方案和工具应解决的问题。设计新工具会扩大当前任务范围时，先征求用户同意。在现有方式可行的情况下，继续推进原任务。
