# Agent Note: 会话索引改用 SQLite

Status: implemented

## Problem

会话索引原先存成单个 JSONL 文件，每次启动全量读入内存。会话数到两千条以后，冷启动要 1.8 秒，而且一次追加写入就要重写整个文件，磁盘 IO 与文件大小同阶。搜索只能线性扫描，无法按时间或工作区过滤。

## Decision

索引持久化改用 SQLite，单文件、单连接、`PRAGMA journal_mode=WAL`。写入按批次提交，每批最多 200 条或 5 秒，任一条件先到即落盘。读取方通过一个查询接口访问，不直接读表；接口只暴露按时间范围、工作区、关键字三种检索条件，返回条数上限由调用方传入。

崩溃恢复依赖 WAL 回放，不再需要读取时的完整性校验。索引与事件日志分离：事件日志仍是追加式 JSONL，是唯一的事实来源，索引可随时删除重建。

## Alternatives considered

**保持 JSONL，加内存索引。** 写入问题解决不了：追加仍需重写整个文件。冷启动能从 1.8 秒降到 0.3 秒，但磁盘放大会随会话数线性恶化，最终仍要换掉。

**引入独立的搜索服务。** 部署成本与这个桌面应用不匹配，且引入一个必须常驻的进程。真实检索需求只有三种过滤条件，SQL 足够。

**把索引和事件日志合并成一份 SQLite。** 事件日志需要可追加、可人工检查、可被外部工具读取，SQLite 会牺牲这三点。合并后也无法"删掉索引重建"。

## Consequences

冷启动从 1.8 秒降到 0.12 秒，会话数增长时基本持平。代价是多了一个二进制格式的持久化文件，需要处理版本升级：表结构变更走 `SCHEMA_VERSION` 单调递增，旧版本只读不迁移，删除索引重建是受支持的操作路径。

写入不再保证单条立即可见，最长延迟 5 秒；依赖"写完立刻可查"的调用方改成先读内存态。

## Verification

`tests/index-store.spec.ts` 覆盖批量上限、时间范围检索、并发读、索引删除后重建、以及旧版本数据库的拒绝路径。冷启动耗时由 `benchmarks/index-open.ts` 跟踪，超过 300ms 即失败。
