# Agent Note: 大文件上传改为分片流式

Status: proposed

## Problem

当前上传接口一次性把请求体读进内存再落盘，2GB 的附件会让进程内存峰值达到 2.4GB，并且在桌面端触发系统换页。用户在中途取消时，已接收的字节仍然写入了最终文件，留下一个看起来完整但内容截断的文件。

## Proposal

接口改为按 `Content-Range` 分片接收，服务端维护一个临时分片目录，全部分片到齐后原子重命名。单个分片上限 8MB，超出返回 413。客户端负责切片与重试，服务端不感知总进度。

取消时删除本次上传的临时目录；超过 24 小时未完成的上传由启动时的一次扫描清理。为兼容旧客户端，保留一次性上传路径一个版本周期，通过请求头 `X-Upload-Mode: single` 显式选择。

## Alternatives considered

**保留单请求，改成流式写入临时文件。** 可以降低内存占用，并在完整接收后再提交文件。连接中断后仍需重新上传整份文件，因此提案选择支持分片重试。

**用第三方对象存储的直传。** 免除服务端改造，但要求用户配置凭据，且桌面离线场景不可用。这条路径作为后续可选能力保留，不作为默认。

**限制一次性上传的文件大小。** 实现成本较低，但会限制现有的大附件使用场景，常见附件超过 500MB。

## Acceptance criteria

- 2GB 文件上传内存峰值不超过 200MB。
- 中途取消后最终路径不存在文件，临时目录被清理。
- 分片乱序到达仍能正确组装。
- 旧客户端走一次性路径时行为与现在一致。

## Risks

分片目录占用磁盘，恶意客户端可以反复发起上传耗尽空间。需要按来源限制并发上传数，并在清理扫描里加总配额。旧路径保留一个版本周期后再删，期间两套代码并存。
