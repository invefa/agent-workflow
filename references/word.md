# Word排版参考

按需阅读。本文保留原Word、python-docx与LibreOffice工具链的模板、算法和经验数值，历史记录未完整保存工具版本。字体、对齐、页宽、目录更新和矢量支持均须按当前交付环境验证；参数是起点，不是所有文档的统一标准。通用要求见[书写与组织](../writing.md#四视觉表达)。

## 一、表格排版

### 1.1 模板默认

以下是原报告模板的具体选择，可按当前模板与阅读需求调整。

- 列宽优先按可见内容和阅读需求分配；内容等量或模板需要时可以等宽。
- 此模板的表头默认居中；其他模板可按阅读需要统一对齐。
- 正文对齐按内容性质判定，不按长度：句子左对齐，标签居中。只把中文句读当作散文信号，英文术语里的半角逗号不算。
- 本模板中以数字序号开头的列默认左对齐。居中会让01、02、09这类序号参差不齐，比左对齐更难读。
- 表头的区分手段从轻到重取舍：先用居中和下沿一条略重的线，不够再考虑别的。不要填充底色，不要加粗，也不要用黑体。黑体笔画本身比正文重，单换字体就等于强调，这几种手段叠起来表头会明显压过内容。
- 宽表默认填满正文宽度；短表可收窄，避免为了铺满而拉大空白。
- 内边距要小、行高要紧凑，表格不能显臃肿。参考值：

| 项 | 参考值 |
|---|---|
| 左右内边距 | 2.5pt |
| 上下内边距 | 0.8pt |
| 单元格内段前段后 | 1pt |
| 正文行距 | 1.15 |
| 表头行距 | 1.05 |

### 1.2 折行要求

避免单元格出现影响阅读的孤立短行；短标签、编号或无法拆分的术语按内容处理，不强行满足固定字数与占比。

### 1.3 列宽算法

要求看着简单，直接按内容比例分配却做不好。完整的做法分四步。

**第一步，量渲染后的文字，再估计字宽。** 宽度必须按实际渲染出来的文字量，不能按源码量。源码里的链接写成`[文件名](文件名)`，长度是渲染结果的两倍多，按源码量会把这一列的下限撑到两倍宽，相邻列被压得频繁折行。

估计字宽时不能用"非汉字一律半角"这种粗估：大写字母与`m`、`w`明显宽于半角均值，`ROMmon`这类混合大小写的缩写会被低估近三分之一，进而导致折行预测偏乐观。按字符分类估：

| 字符 | 占宽 |
|---|---|
| 汉字与全角符号 | 1.00 em |
| 大写字母 | 0.68 em |
| 小写字母 | 0.52 em |
| 数字 | 0.50 em |
| 空格 | 0.26 em |
| 其他半角符号 | 0.34 em |

**第二步，分清两个宽度口径。** 这是最容易出错的地方：

- 列宽 = 单元格实际宽度，含左右内边距。
- 文本区宽度 = 列宽减去两侧内边距。

分配列宽时用的是文本区宽度，设给单元格时用的是列宽。混用会让折行预测整体偏乐观一个内边距的量，表现为"预测一行放得下、实际差一点放不下"，末行甩出一两个字。

折行判断再加上0.94的安全系数。字宽是估算值，与实际排版总有偏差，宁可略早判定换行。

**第三步，定义代价函数。** 表格高度由同一行各列中行数最多的那格决定，所以不能按列独立求和：

```text
整表代价 = 各行最大行数之和 + 末行过短惩罚之和 * 权重
```

末行过短惩罚按绝对字数计，不按占列宽的比例。比例会失真：末行同样是3个字，在宽列里占比很小却和窄列一样难看。罚法是"末行不足3个字时，按缺的字数计"，权重取3.0。

权重需要实测标定。把权重从3提到12，末行过短的数量一个都不再降，说明瓶颈是固定总宽，继续加权重没有意义。

**第四步，坐标下降分配。** 先按内容量给初值，再用半个字宽为步长在列之间转移宽度：

```text
对每一对列 (a, b):
    试把半步从 a 移到 b,总宽不变
    整表代价下降则接受,否则还原
直到一轮下来没有任何转移被接受
```

保持总宽不变，表格自然填满正文宽度。

这里有一个退化情形必须单独处理。当每列内容都放得下时，整片区域的代价相同，下降算法找不到改进方向，会停在初值上，把富余宽度留在任意一列。表现为同一套算法在有的表上分配合理，在另一些表上却失衡。先判断是否所有列都放得下，若是则不存在折行取舍，直接把富余宽度按内容量比例摊开。

### 1.4 折行兜底

列宽确定后，逐格检查折行结果。若末行过短，必要时计算均匀断行并显式插入换行符；内容频繁变化或模板能正确重排时保留自动折行，避免固定换行反而造成溢出。

留余量：显式断行的目标宽度是文本区的82%，断完之后还要检查每行不超过86%，否则估算偏差会让断好的行再次溢出，反而更难看。

这一步的效果明显，实测数据：

| 末行字数 | 处理前 | 处理后 |
|---|---|---|
| 不足3个字 | 43处 | 3处 |
| 不足2个字 | 12处 | 0处 |

### 1.5 其他表格属性

- 表头跨页重复（`w:tblHeader`）。
- 单行不被页面截断（`w:cantSplit`）。
- 表格用固定布局（`w:tblLayout type="fixed"`），同时设`tblGrid`与每个单元格的宽度。
- 表头行下沿加稍重的边线，与表体区分。
- 边线按边合并，不能每次调用都重建整组。只加一条下沿线时若把整组删掉重建，单元格其余的边会被一并抹去；表格外框失去显式设置后会回退到宿主程序内置样式的黑色边框，整张表因此变重。
- 边线元素要插在宿主元素规定的子元素位置上，不能一律追加到末尾，否则生成的文档可能被判定为损坏。

## 二、报告排版

### 2.1 文档结构

需要正式Word报告且无其他模板时，可按下述结构组织；短文不必额外加封面与目录：

| 部分 | 内容 |
|---|---|
| 封面 | 标题、副标题、细线、文档元信息 |
| 目录 | 章节标题加点线引导加页码，一级二级都列 |
| 正文 | 章节、段落、图、表 |
| 页眉页脚 | 页眉放文档名，页脚放页码；封面不显示 |

正文用宋体10.5pt首行缩进两字，标题用无衬线体加粗，层级靠字号区分（一级15pt，二级13pt）。

### 2.2 目录页码

原Word与LibreOffice转换环境没有按预期更新目录域，设置`w:updateFields`和`w:dirty`仍只得到占位文字。先核对当前宿主能否更新目录，再选择是否采用以下兜底。

原脚本通过逐段截断渲染估算页码并缓存，代价较高：

1. 把文档依次截断到第k个标题为止，转一次PDF。
2. 该PDF的总页数就是第k个标题所在页。
3. 截断只删除标题之后的内容，不影响之前的分页，所以结果与最终文档一致。
4. 把结果缓存成JSON，后续重建直接复用，不必每次重算。

取页数用渲染命令比读PDF内部结构稳，注意渲染命令在输出目录已存在时会直接失败，每次要换一个干净目录。

### 2.3 图片嵌入

原python-docx环境直接插入SVG会抛`UnrecognizedImageError`。以下是当时保留矢量图的改包方案；使用前核对当前库与宿主能力：

1. 先按普通位图插入（这一步同时生成必需的PNG兜底部件）。
2. 解包，把SVG加入`word/media/`。
3. 在`word/_rels/document.xml.rels`里加一条image关系。
4. 在`document.xml`的`a:blip`节点内追加`a:extLst`，里面放`asvg:svgBlip`指向SVG。

原方案面向能识别SVG扩展的宿主，旧宿主使用PNG兜底；SVG和foreignObject的支持需要实际验证，不能只按版本名称推断。原drawio的部分标签带有位图回退，因此SVG文件也不保证所有文字都是矢量。嵌入所需的PNG由figures-src中的源文件临时导出到构建目录，不混入正文引用的figures；当前SVG标签表现见[绘图参考](diagrams.md#四svg标签与总线连线)。

放图宽度按`画布宽度 / 100`英寸换算，使正文文字落在9pt左右，同时保证打印分辨率。

验证矢量的方法是把PDF按400DPI渲染再裁一块看，文字边缘锐利即证明是矢量；若是位图，这个倍率下必然糊。

### 2.4 公式

python-docx不封装公式，要直接写OMML。先判断需要多整齐，再选做法：

| 目标 | 做法 | 代价 |
|---|---|---|
| 多行方程按等号对齐 | `m:eqArr`，每行一个对齐点 | 变量列对不齐，左端参差 |
| 符号、系数、变量各成一列 | 排版成图后按原位插入 | 不可编辑，改公式要重排 |
| 同上且必须可编辑 | 表格承载 | 单元格内边距把项与项之间撑开，观感差 |

对齐点是run属性`m:rPr/m:aln`，表示该run从对齐处开始；写成`m:e`的子元素会让Word判定文件损坏。Word每行只认一个对齐点，写多个不会排出多列。

排版成图时按单元格定位：先量每段文字的渲染宽度，取每列最大值作为列宽，再逐列累加坐标；符号列与数字列右对齐，变量列左对齐，缺项留空。插入宽度取`像素/输出dpi*2.54`，字号才与正文一致。mathtext的间距用`\;`，`\,`不生效。

Word支持在界面里导入LaTeX（Microsoft 365可识别`\begin{aligned}`等环境），但这条转换只走界面，没有脚本接口，不要假设能程序化复用。

### 2.5 代码块

Word没有代码块样式，用段落格式模拟：等宽字体、固定行距（9pt字配12pt行距）、浅灰底、左右缩进、无首行缩进。语法着色按词法分析分段，只给关键字、字符串、注释三类颜色，其余保持黑色。

代码从源文件读入后原样输出，不在文档里手工复制，避免交付物与运行版本脱节。行宽按代码实际最长行控制，超出正文宽度时缩字号或拆行，不要为此压缩整页边距。
